# Machine/material candidate index

**Design inventory, 2026-10-28; not an implementation or survival-acquisition report.** This is a *family-level* index of machines, powered apparatus, processing multiblocks, vehicles and infrastructure in the pack that could inherit Tinkers' material-bearing parts or have an existing tier/upgrade replaced. Variants of the same mechanism are grouped; decorative blocks, ordinary storage furniture, weapons, armour, and non-machine creatures are not individually enumerated. The scope includes the 244 `mods/*.pw.toml` pack inputs, the 50 local custom-mod JARs visible during the inspection, their cached upstream JAR language/registry names, pack scripts/configs and selected local sources. A named upstream block is **not** proof that it is obtainable, active in a previously accepted ZIP, or appropriate for replacement. A runtime recipe/registry and owning-mod behavior audit is still required before implementing any entry. This document does not activate sibling-source-only mods.

Read with [Aspirational features](aspirational-features.md#tinkers-parts-as-widely-usable-manufacturing-components), [Progression](progression.md), [Balance policy](balance_policy.md), [Content ownership](content_systems.md) and [Crafting policy](crafting_policy.md). The proposed material vocabulary is **Tinkers' existing stat roles and traits**, applied only to relevant part types; do not equate mining tier with a general machine level or invent physical properties that those stats do not represent.

**Disposition key:** **R** = existing explicit tier/upgrade or graded part is a serious replacement candidate; **E** = no verified material tier, but a promising material-sensitive machine; **H** = hybrid: preserve the distinct capability/interface while considering material-sensitive performance; **L** = low-priority/awkward; **X** = excluded by current pack policy or incompatible with this design. R and E are *proposals*, not claims that an API for dynamic machines already exists. For R, replacing the native system is conditional on preserving valid saves, inputs, recipes, UI and player choices. A material-aware ingredient alone is not machine inheritance.

## Cross-checks, priority and hard limits

1. **Best true tier-replacements:** Rail Beetle performance modules; Complicated Bees Gyrofuge graded processing/speed/efficiency/extraction units; PneumaticCraft compressors/tubes; Create Sifter meshes; Pretty Pipes speed/extraction. These *currently have* graded mechanisms; material integration must still preserve their functional axes.
2. **Best chemistry-to-part demonstrations:** an airtight seal/liner installed in the existing Basin/Fluid Mixer/Thermopneumatic Plant; a TCon-cast part used in Rail Beetle brakes/drawgear; a PowerGrid rotor/winding; a Heat Sync heat pipe or exchanger. These bridge actual chemistry to saved machine behavior rather than changing a recipe ingredient alone.
3. **Do not turn capability into a material number:** machine blocks are batched **root proofs**, not quality grades; pressure, electric supply, heat, topology, room size, program logic, surveying, bees' environment and magical rituals are distinct constraints. Early Create/TCon remains common workshop competence; keep independently deep practices accessible.
4. **Do not reactivate closed systems:** Create Diesel crude extraction/distillation, alternate stationary FE generators, native AE generation, Occultism remote/infinite storage/mining, capped flight upgrades, potion brewing and unlimited matter routes have explicit policy cuts. Their registration/localization in an upstream JAR is not an invitation to wire them back in.
5. **Pre-implementation evidence per row:** check exact registry ID and obtainable acquisition routes (recipes, loot, world finds, trades), owner/source/config, actual current tier behavior, safe part roles and stat base-versus-modifier mapping, save/placement/multiblock persistence, drop/recovery, existing upgrade coexistence/migration, EMI explanation and runtime effect. Map a polymer's qualitative fit to **existing TCon material stats or traits**; if heat/chemical resistance is desired, author and explain that additional role explicitly rather than pretending it is `mining_tier`.
